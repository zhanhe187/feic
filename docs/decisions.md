# 决策记录

按「背景 → 决定 → 代价」记录几个会影响实现走向的选择。写下来的意义是：被追问时能讲清为什么，
而不是复述代码。

## ADR-01 提醒去重交给数据库唯一索引

**背景**：生命周期的提醒由定时任务生成。任务可能重跑（补数据、改配置重启），部署可能是多实例。

**决定**：提醒表对「员工 + 提醒类型 + 提醒日期」建唯一索引，插入语句用插入忽略，返回受影响行数为 0 就说明今天已发过。

**理由**：应用层「先查再插」有并发窗口，两个实例同时查到「没有」就会各插一条；唯一索引是数据库级约束，绕不过去。

**代价**：插入忽略会一并吞掉非重复键的错误（字段超长、外键失败），排查时容易误以为「已经存在」。
更稳的写法是只忽略重复键错误，或在插入前显式校验长度。

**位置**：`workforce/sql/02_lifecycle.sql`、`wfserver/wf-mapper/src/main/resources/mappers/EmployeeLifecycleReminderMapper.xml`

## ADR-02 状态机做成表驱动，接口按动作拆

**背景**：工单有 5 个状态。最容易的写法是一个 `update status` 接口，前端传什么就存什么。

**决定**：把「当前状态 + 动作 → 目标状态」写成一张合法流转表，所有改状态的动作统一过这张表校验；
接口按动作拆成派发、处理、驳回、关闭，每个动作有自己的必填参数与副作用。

**理由**：状态乱跳是这类系统最常见的脏数据来源，而通用的 update 接口无法表达「驳回必须填原因」这类约束；
按动作拆之后，校验、留痕、通知都挂在各自的动作上，测试也按动作写。

**代价**：接口数量变多；新增一条流转要同时改表和对应的动作实现。

**位置**：`desk-system/.../system/service/TicketStateMachine.java`、`desk-admin/.../controller/it/ItTicketController.java`

## ADR-03 JWT 只装会话标识，权限放 Redis

**背景**：JWT 的卖点是无状态，但如果把角色和权限写进 token，改权限要等 token 过期才生效，也没法强制下线。

**决定**：token 里只放随机会话标识与非敏感声明，用户信息、权限、过期时间存 Redis；
每次请求取一次登录态，剩余有效期不足 20 分钟时刷新。

**理由**：企业系统的权限会变，禁用账号要即时生效，这些需求比「省一次 Redis 查询」重要得多。

**代价**：每个请求多一次 Redis 读；Redis 故障时登录态校验会失败，需要靠部署冗余而不是降级。

**位置**：`desk-framework/.../framework/web/service/TokenService.java`

## ADR-04 数据权限下沉到 Service 查询条件

**背景**：菜单权限只能控制「能不能进页面、能不能调接口」，员工仍可以直接调接口拿别人的工单。

**决定**：在 Service 层根据当前角色，把申请人 / 处理人条件注入查询；详情与更新同样带归属条件，
查不到就按不存在处理。

**理由**：越权防护必须在服务端最后一道入口，且「不存在」比「无权限」更安全，避免被用来枚举 id。

**代价**：每个查询都要记得加条件，容易漏；漏了不会报错，只能靠测试用例覆盖。

**位置**：`desk-system/.../system/service/impl/ItTicketServiceImpl.java`

## ADR-05 AI 只做语义抽取，不碰状态与优先级

**背景**：工单描述是自由文本，真正缺的是可筛选的结构化字段；但让模型决定状态和优先级风险很大。

**决定**：模型只输出设备、现象、影响面、已尝试四个槽位；优先级由影响面按规则推导；
状态与处理人由服务端强制设定，前端传什么都覆盖。

**理由**：模型对「紧急」没有责任，用户写「很急」就会造成优先级通胀；而槽位是可以在原文里核查的。

**代价**：模型的作用被限制在很窄的范围内，看起来「不够智能」，但换来的是可解释和可审计。

**位置**：`desk-system/.../system/ai/PriorityRule.java`、`ItTicketServiceImpl#sanitizeAiSlots`

## ADR-06 同步交互不重试，失败即降级

**背景**：员工提交工单是同步等待，模型调用最坏要 8 秒。

**决定**：超时 8 秒，不重试；无 Key、超时、5xx、坏 JSON、配额用尽、熔断打开，一律降级到规则引擎，
返回 `degraded=true` 与提示语。

**理由**：重试会把最坏等待变成 16 秒，用户体感不可接受；瞬时抖动应该由降级和熔断吸收，
而不是让用户多等一倍。

**代价**：偶发失败也会走降级路径，抽取质量下降；规则引擎必须能产出等价结构，否则前端要分支处理。

**位置**：`desk-system/.../system/ai/AiIntakeService.java`、`LangChain4jClient.java`

## ADR-07 熔断用固定窗口，不做半开探测

**背景**：外部模型不可用时，每个请求都要白等 8 秒才知道失败。

**决定**：连续 3 次失败打开熔断，5 分钟内的请求直接走规则引擎；时间窗口结束后自动放行，
成功即恢复。

**理由**：场景是「外部服务短时间不可用」，固定窗口加自动重试已经够用；半开状态要额外维护探测计数与状态迁移，
收益很小。

**代价**：恢复探测不够精细，窗口内可能仍在故障期；用少量请求换实现简单，是有意的取舍。

**位置**：`desk-system/.../system/ai/AiBreaker.java`

## ADR-08 历史工单检索用 BM25，不引入向量库

**背景**：IT 处理工单时想看历史同类单子怎么解决的。

**决定**：中文按 2-gram、ASCII 按单词切分，字段加权后做 BM25 打分，按最高分归一化并卡相对相关度阈值；
引用真实工单号与处理说明。

**理由**：这是关键词匹配问题，BM25 毫秒级、零调用成本、结果可解释；向量库在几百条语料上没有召回优势，
却要多一套运维和一次 embedding 调用。

**代价**：不做语义泛化，「笔记本开不了机」和「电脑无法启动」可能匹配不上；量级上来先换数据库全文索引。

**位置**：`desk-system/.../system/ai/KbRetriever.java`

## ADR-09 选 LangChain4j 1.13 而不是 Spring AI

**背景**：项目底座是 Spring Boot 4.0.6，要接一个 OpenAI 兼容的模型服务。

**决定**：用 LangChain4j 1.13.0，并在业务与框架之间放一层 `AiLlmClient` 适配器。

**理由**：Spring AI 2.0.x 硬依赖 Spring Boot 4.1.x，1.1.x 依赖 3.5.x，为接 AI 去升底座会牵动
druid、mybatis、pagehelper、springdoc 一整串依赖；LangChain4j 1.13 要求的 Jackson 版本（2.21.1）
不高于 Boot 管理的 2.21.2，不会出现运行期版本降级。

**代价**：LangChain4j 的 API 与 Spring 生态的集成度不如 Spring AI，需要自己写配置与生命周期管理。

**位置**：`desk-system/.../system/ai/LangChain4jClient.java`、`desk-system/pom.xml`

## ADR-10 组合索引的列顺序：当时的写法与现在的认识

**背景**：待办查询的条件是「工作状态 + 到期时间范围 + 部门」。

**决定**：当时建的是 `(workState, conversionTime, departmentId)` 与 `(workState, endContract, departmentId)`。

**复盘**：这是「等值在前、范围在后」的直觉写法，但范围列放在中间，后面的部门列只能做索引条件下推过滤，
不能参与定位。更严谨的顺序是把两个等值列都放前面，范围列收尾：
`(workState, departmentId, conversionTime)`，三列都能参与定位。

**怎么验证差别**：看 `EXPLAIN` 的 `key_len` —— 如果只覆盖到日期列，说明部门列没有参与定位；
部门选择性高时换顺序能明显降低扫描行数。

**代价与现状**：这两条索引已经在用，改顺序要评估写入影响，所以先记录认知，没有立即重建。

**位置**：`workforce/sql/02_lifecycle.sql`
